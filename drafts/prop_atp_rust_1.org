#+title: Automated theorem proving for propositional logic (part 1)

This is the first part of a series covering automated theorem proving techniques
for propositional logic. The series aims at being a foundational and practical
guide introduction to this subject. The practical aspect means we will implement
everything, and I chose =rust= to do that[fn:1].

This first part will be dedicated to the abstract syntax of propositional logic,
and its concrete counterpart, together with its parsing and pretty-printing.

Although this seems straightforward on the surface, it does involve a number
of concepts, and comprises quite a number of lines of code.

* Mathematical syntax 

Let's start by giving a mathematical definition of the syntax of propositional
logic. It is an /inductive/ definition where the base element is the /atom/ and
the logical connectors $\neg, \vee, \land, \implies, \iff$

\[
  prop ::=
       | atom 
       | \neg\; prop
       | prop \vee prop
       | prop \land prop 
       | prop \implies prop
       | prop \iff prop
\]

This is a maximal view of the type definition. You might indeed know that:
- $P \implies Q \approx \neg P \vee Q$;
- $P \iff Q \approx (P\implies Q) \land (Q \implies P) \approx (\neg P \vee Q)  \land (\neg Q \vee P)$.


We'll use these 2 facts to reduce the size of the definition of the abstract
syntax[fn:2]  Since we aim at showing simple automated theorem proving techniques at
work, we could also have chosen.

** Remark

Since this series is about automated theorem proving, we could also have
proven these facts with the techniques we'll talk about later. We preferred to
keep the core inductive type for abstract syntax shorter to make code examples
smaller and less redundant. I chose to keep $\land$ *and* $\lor$ to make the
discussion about normal forms a bit simpler.

* Concrete syntax

** Definition

  The so-called /concrete/ syntax corresponds to the characters we write when
  defining a logical formula. Let's define the concrete syntax by an equivalence
  table, borrowing elements from the [[https://rocq-prover.org/][Rocq]] syntax.

  In the end, we have the following equivalence table:

  |----------------+----------+---------------------------------------------------------------------|
  | Mathematical   | Concrete | Abstract                                                            |
  |----------------+----------+---------------------------------------------------------------------|
  | $P$            | =P=      | =Atom("P")=                                                         |
  | $\neg P$       | =~P=     | =Not(Atom("P"))=                                                    |
  | $P \vee Q$     | =P \/ Q= | =Or(Atom("P"), Atom("Q"))=                                          |
  | $P \and Q$     | =P /\ Q= | =And(Atom("P"), Atom("Q"))=                                         |
  |----------------+----------+---------------------------------------------------------------------|
  | $P \implies Q$ | =P => Q=  | =Or(Not(Atom("P")), Atom("Q"))=                                     |
  | $P \iff Q$     | =P <=> Q= | =And(Or(Not(Atom("P")), Atom("Q")), Or(Not(Atom("Q")), Atom("P")))= |
  |----------------+----------+---------------------------------------------------------------------|


** Parsing

  Parsing transforms concrete syntax into abstract syntax, or produces an error
  in case of failure to do so.

  We will roll our own [[https://en.wikipedia.org/wiki/Recursive_descent_parser][recursive descent parser]], where we will encode the
  precedences of operators goes as follows: =<=> < => < \/ < /\ < ~=. The
  associativity is also encoded in the parser: a production that loops on
  itself, like =iff=, =or= and =and=, folds its operands to the /left/, whereas
  one that recurses on the right, like =implies=, folds them to the
  /right/. Implication is the odd one out here, and this matches the usual
  reading of $P \implies Q \implies R$ as $P \implies (Q \implies R)$. For
  the biconditional, the choice is ours to make[fn:4]. And finally, we also
  allow parentheses whose contents define its own precedence island.

  Schematically, here is a semi-formal definition of our parser: 

  #+name: semi_formal_parser
  #+begin_src text
    prop     → iff
    iff      → implies (IFF implies)*
    implies  → or (IMPLIES implies)?
    or       → and (OR and)*
    and      → not (AND not)*
    not      → NOT not | atom
    atom     → IDENT | LPAREN prop RPAREN
  #+end_src

  The uppercase letter define /tokens/, that is, the words of the
  language. Operators are keywords in our case (we will not allow to re-define
  them). How do we obtain tokens to parser? Through /lexing/!

** What goes around comes around

   A pretty-printer and parser needs to be bound by some form of inverse
   relation.  Let =s' = print(parse(s))=. Then either we have =s' = s=, or, more
   usually, a weaker form of equality on abtract syntax trees =parse(s') =
   parse(s)=, since the former might hold only for a subset of parsable inputs.

   For example, in propositional logic $(P \land Q) \lor R$ reads the same as $P
   \land Q \lor R$ but the string representation is different. If we accept
   parentheses but permit omitting them, we can only enforce the weaker
   relation.
